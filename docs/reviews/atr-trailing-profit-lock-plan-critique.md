# Critique: ATR-Scaled Trailing Stop + Profit-Lock Plan

Date: 2026-08-17 · Scope: `docs/plans/atr-trailing-profit-lock-2026-08-17.md` vs. the oracle-plan export `prompt-exports/oracle-plan-2026-08-17-223016-atr-trailing-profit-63ea.md`, spot-checked against the actual source.

## Spot-check verdicts (plan's line-level claims vs. code)

All five named seams check out. The plan's core "the files are ground truth, the notes are stale" correction is **correct**.

- **(a) Confirmed.** `EnableATR: true` in `GetDefaultStrategyConfig` (`store/strategy.go:1062`). `vergexHoldRules()` (`kernel/engine_prompt.go:263-269`) reads *"Set stops and targets from each coin's own 15m ATR14 … stop-loss at 1.5× … take-profit at 2×"* with **no** −3%/+8% literals. The planning agent's note claiming `EnableATR=false` and stale prompt text was wrong; the plan's refusal to re-touch the prompt text is justified. One caveat to the plan's clean-room framing: fixed-% stop guidance still exists elsewhere in the same file — `"Per-trade stop-loss: 1.5-3% from entry"` at `engine_prompt.go:473`, outside `vergexHoldRules()`. The plan's "no −3%/+8%" claim holds only because it scopes the change to `vergexHoldRules()`, which it does explicitly. Worth a one-line note so a later reader doesn't conclude the whole prompt is ATR-clean.
- **(b) Confirmed.** `checkPositionDrawdown` is called **only** from the ticker (`auto_trader_risk.go:50`); the existing test file tests `shouldDrawdownClose`, not `checkPositionDrawdown`, so the `()`→`(positions)` signature change is safe. `peakPnLCache` stores margin-basis P&L: `currentPnLPct := pricePnLPct * float64(leverage)` then `UpdatePeakPnL(...)`. The plan's claim that a separate **peak-price** map is required is correct.
- **(c) Confirmed.** `CancelStopOrders` (`hyperliquid/trader_orders.go:411`) cancels every pending order for the coin (TP included — the SDK `OpenOrder` exposes no trigger field). `attachStopLossTakeProfit` (`auto_trader_orders.go:107`) is place-once with no cancel; there is no cancel+re-place wrapper anywhere. The plan's mandatory `CancelStopOrders → SetStopLoss → SetTakeProfit` sequence is required and correctly ordered.
- **(d) Confirmed.** `attachStopLossTakeProfit` is invoked with `"LONG"`/`"SHORT"` (uppercase) at `auto_trader_orders.go:254`/`:379`; Hyperliquid's `SetStopLoss`/`SetTakeProfit` compute `isBuy := positionSide == "SHORT"` (uppercase-sensitive, `trader_orders.go:1021`/`:1071`); the monitor reads `side` lowercase `"long"`/`"short"`. The casing mismatch the plan flags is real.
- **(e) Internally consistent.** `TrailStopTarget`: long arms at `peak ≥ entry + mult·ATR`, `trail = peak − mult·ATR` (equals `entry` at the arming instant → break-even); short mirrors. Monotonic given a monotonic peak. `moveTrailingStopLoss`'s cancel→SL→TP ordering is the only correct sequence given (c).

Minor pre-existing quirk the plan can ignore but should know: the `Trader` interface docstring (`trader/types/interface.go:77`) says `CancelStopLossOrders` "don't delete take-profit when adjusting stop-loss," which **contradicts** the Hyperliquid implementation (it forwards to the coin-wide cancel). The plan correctly trusts the implementation, not the doc.

## 1. Implementation-bearing content lost / weakened / generalized vs. the export

The plan preserves almost all implementation content. Two spots soften or drop it:

- **The export's explicit open-question "decide hardcode vs. config field" is resolved by fiat.** The plan chooses `ATRTrailMultiplier` config field with `Min/Max` clamps + `StrategyClampWarnings` + default 1.0. This is a defensible resolution and matches the file's existing parameterization convention (`ATRStopMultiplier`/`ATRTargetMultiplier`). No issue — but it is a *new* decision not present in the confirmed scope; the plan should note it was an open question, not a confirmed requirement, so the scope doesn't silently grow. Low severity.
- **The drawdown-arm design generalizes the export's "~1×ATR" into a `drawdownArmPct` helper with a hardcoded 1×ATR and a 1.5% fallback.** Fine, but it introduces a second, independent "1×ATR" constant that is **not** the same multiplier the trail uses (`atrTrailMultiplier`, default 1.0). If a user sets `ATRTrailMultiplier: 2.0`, the trail arms at +2×ATR while the drawdown close still arms at +1×ATR. The plan never reconciles these two "arm" thresholds. See Question 3 below.

## 2. Under-specified seams, unresolved decisions, contradictions, missing deps

**(High) Side-case propagation into the exchange layer.** The plan's key-normalization is incomplete. `checkTrailingStops` iterates positions from `GetPositions()`, where `side` is lowercase (`auto_trader_risk.go:70`). §3.6 step 7 calls `at.moveTrailingStopLoss(symbol, side, quantity, newStop, state.tp)`, and §3.4 forwards that `side` straight into `at.trader.SetStopLoss(symbol, side, ...)` / `SetTakeProfit(...)`. But Hyperliquid's `isBuy := positionSide == "SHORT"` is case-sensitive: a lowercase `"short"` yields `isBuy=false`, so the short's SL/TP are placed as **sell** trigger orders — the wrong leg, likely an immediately-triggering or reversed order. The plan lowercases only for the **map key** (`positionKey`); it never states that the exchange-facing `side` argument must be **uppercased** before the `Set*` call (or that the wrapper should take `isLong` and derive the exchange side itself). Every existing call site passes uppercase (`interface.go:189/:191`, `auto_trader_orders.go:254/:379`). This is precisely the short-side sign bug class the merged critique warned about, and it is under-specified here. **Resolution required before implementation.**

**(High, missing dep) The `shouldDrawdownClose` signature change breaks an existing test.** `trader/auto_trader_risk_test.go:22` calls `shouldDrawdownClose(c.pricePnLPct, c.drawdownPct)` (2 args). The plan's 3-arg signature `(pricePnLPct, armPct, drawdownPct)` will not compile against it. The plan's Tests section and Verification gate name `atr_scalp_test.go`, `auto_trader_sltp_test.go`, `engine_prompt_test.go` as "existing … pass" but **omit `auto_trader_risk_test.go`**, which must be rewritten. Moreover that test's intent ("+0.5% must never arm; armed only from a real price move") must be preserved under ATR-relative arming — the rewrite is non-trivial, not mechanical.

**(Medium) Debug-log branch coupled to the removed constant.** The plan says "flat 5.0 gone," but `drawdownClosePriceGainPct` is also referenced by the `else if pricePnLPct > drawdownClosePriceGainPct` debug/telemetry branch (`auto_trader_risk.go:138`). If the constant is removed, this branch must be re-expressed (e.g. against `armPct`); if it's kept only for the log, the "close to condition" telemetry silently stops covering the new 1×ATR arming range (2–3% scalps), defeating the debug signal the plan's own manual-replay gate wants to observe. Plan doesn't address it.

**(Medium) "Never moves TP" is overstated on the fallback seed path.** §3.3's fallback seeds `{stop, tp} = ATRStopTarget(entry, atr14, stopMult, targetMult, isLong)` — `tp` is **recomputed**, not read from the exchange. §3.6 step 7 then claims `state.tp` is "the recorded open TP — never recomputed, never moved." On a fresh process with a position already open, `state.tp` *is* recomputed, and the first trail move re-places it. For an ATR-derived open this equals the real TP (fine), but a manually-widened TP would be narrowed on the first move — contradicting the plan's "never touches TP" guarantee, which only strictly holds on the primary open-time seed. Either scope the guarantee to the open-time path or make the fallback adopt only the stop and leave TP untouched until the open-time path establishes it.

**(Low) Rounding not modeled in the source-of-truth.** `SetStopLoss`/`SetTakeProfit` round prices to a valid Hyperliquid tick internally (`roundPriceForOrder`), but the plan's `trailState.stop`/`.tp` store the **unrounded** values. The epsilon gate (`1e-4` relative) is larger than typical tick spacing, so this is likely harmless, but it means `state.stop` can differ from the actually-placed SL by a tick for one extra cycle. Worth a comment, not a redesign.

## 3. Code disproves / not required / simpler design

- **No correction needed on the plan's stale-notes thesis** — the code backs it (spot-check (a)).
- The plan correctly **does not** re-touch `ensureStopLossTakeProfitDefaults`, `ATRStopTarget`, the eligibility filter, or the ATR config fields; the export agreed. Nothing to strip.

## 4. Missing requirements / edge cases / architecture problems (absent from both)

- **Concurrency is real, not "contention-free."** `attachStopLossTakeProfit` (which seeds `trailState`) runs from the autopilot open path (`executeOpen*WithRecord`), i.e. a **different goroutine** from the monitor ticker that reads/writes `trailState`. The plan says "mutexes are protective but contention-free." They are **not** contention-free: an open can land mid-tick. The mutexes are sufficient (good), but the plan should not claim zero contention — and `checkTrailingStops` must read `trailState` under `trailStateMu` when it seeds/mutates, consistent with the open-time write. Also note `trailStateMu` is a plain `Mutex` while `peakPriceMu` is `RWMutex`; justify or unify.
- **Failure atomicity across the three sequential SDK calls.** The plan documents that a mid-sequence failure leaves state stale and retries next tick, and explicitly does **not** compensate-close. Good. But it does not state what happens if `SetStopLoss` succeeds and `SetTakeProfit` fails after a cancel: the position has a new SL but **no TP** for up to a minute. The plan says "or has a new SL but possibly no TP" and accepts it — acceptable, but the "retry next tick" loop will re-place TP on the next tick (since state.stop wasn't updated, the trail re-cancels/re-places). This converges but wastes a cancel+place each tick until TP lands. Consider whether to update `state.stop` optimistically so the retry re-places only TP. Currently unspecified.
- **Emergency-close vs. trail ordering is hand-waved.** §3.6 step 1 says "drawdown first, skip closed symbols" — but the drawdown close and the trail both run from the same pre-fetched `positions` slice; the trail loop must know which symbols the drawdown loop closed. The plan says "track closed symbols" but gives no mechanism (set/map). And `emergencyClosePosition` currently does **not** clear `peakPnLCache` (clearing happens in the caller after success, `auto_trader_risk.go:137`); the new `trailState`/`peakPrice` GC (§3.6 step 8) is the real cleanup, so an explicit clear in `emergencyClosePosition` (listed in the file-by-file row) is redundant but harmless — just don't double-own cleanup. Specify the single cleanup owner.
- **No test for the wrapper's error atomicity or the no-TP-after-partial-failure state.** The plan tests wrapper order + TP re-place, but not the partial-failure retry path or the "state not updated on failure" invariant it asserts in §3.4. Add one.

## 5. Questions that would change design or order

1. **What case does `moveTrailingStopLoss` pass to `SetStopLoss`/`SetTakeProfit`?** Uppercase `"LONG"/"SHORT"` (matching the exchange contract) or lowercase from `GetPositions()`? This is the single highest-risk seam — get it wrong and shorts place reversed trigger orders. (Resolves finding #2.)
2. **On the fallback (restart) seed, should TP be re-derived (`ATRStopTarget`) or left untouched?** The plan's "never moves TP" guarantee depends on the answer. Decide explicitly; otherwise the restart path silently narrows a manual/wider TP on the first move.
3. **Are the two "1×ATR" arm thresholds meant to be the same value?** The trail arms via `atrTrailMultiplier` (configurable, default 1.0) while `drawdownArmPct` hardcodes 1×ATR and is not configurable. If a user raises the trail multiplier, the drawdown close still arms at 1×ATR. Should `drawdownArmPct` be derived from `atrTrailMultiplier()` for a single source of truth, or is the divergence intentional?
4. **On partial wrapper failure (SL placed, TP not), should `state.stop` update optimistically** so the next tick re-places only TP instead of a full cancel+re-place? Affects the retry loop's efficiency and the unprotected-window duration.
5. **Should `shouldDrawdownClose`'s new 3-arg form take `armPct` as a plain float, or should `drawdownArmPct` be the caller-injected seam** (so the existing 2-arg test can be preserved/adjusted with minimal churn)? Minor, but it determines how much of `auto_trader_risk_test.go` is rewritten.

## Bottom line

The plan is well-grounded: all five spot-checks confirm its reading of the code, and its correction of the stale architecture notes is correct and should stand. The concrete gaps to close before/while implementing: (1) specify the uppercase exchange-facing `side` in `moveTrailingStopLoss` (short-side correctness), (2) budget for rewriting the now-breaking `auto_trader_risk_test.go`, (3) reconcile the debug-log branch and the two "arm" multipliers, and (4) scope the "never moves TP" guarantee to the open-time seed path. None invalidate the design; all four are implementation-bearing.
